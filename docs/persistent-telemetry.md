# Persistent telemetry demonstration

This extension connects the dashboard to a Fastify API and SQL Server. All measurements in this demonstration are synthetic. The simulator and local MCP bridge remain available.

## Local setup

The GitHub Pages workflow sets `VITE_DEMO_VIDEO_URL=./frontend-demo.webm` and copies the retained `evidence/local/frontend-walkthrough-20260920.webm` into the Pages artifact. It checks that the copy is byte-identical. The public control is labelled **Demo video** and opens a recording of the current light interface running on the browser simulator. It does not represent Azure execution. Old `?source=cloud` links keep the simulator active without requesting an API. The recording remains usable after Azure is closed; this change does not cancel the subscription.

Leave both `VITE_DEMO_VIDEO_URL` and `VITE_CLOUD_DASHBOARD_URL` unset for local API and Azure builds so Cloud uses the same-origin API and Microsoft login route. The older `VITE_CLOUD_DASHBOARD_URL` navigation option remains supported for separately configured deployments. When both URLs are set, recorded evidence takes precedence. These variables are public navigation URLs, not credentials.

Use Node.js 22 and SQL Server 2022 Developer in Docker. Install the frontend and API independently:

```sh
npm ci
npm run build
cd api
npm ci
npm run build
```

Create a dedicated SQL database named TelemetryProof. For isolated integration tests, create TelemetryProofTest and a separate empty database for each recovery test. Never point tests at a database containing data to preserve.

Supply these process environment variables through your shell or local secret store. Do not commit their values:

| Variable | Local value |
| --- | --- |
| SQL_CONNECTION_STRING | SQL Server connection string for TelemetryProof |
| AUTH_MODE | local |
| LOCAL_READER_TOKEN | Random secret of at least 32 characters |
| LOCAL_OPERATOR_TOKEN | Different random secret of at least 32 characters |

The local SQL connection may trust the development container's certificate. Azure uses certificate validation and managed identity. The API listens on 127.0.0.1:4100 locally.

From api/:

```sh
npm run migrate
npm run dev
```

From the repository root in another terminal:

```sh
npm run dev -- --host 127.0.0.1
```

Open http://127.0.0.1:5173/?source=cloud and enter the local token. It remains in React memory, is cleared from the input, and must be entered again after a reload. The screen explicitly says local API until the application is actually deployed on Azure. The development proxy preserves the browser Host so same-origin writes work.

From the sibling mcp-live-telemetry repository, set TELEMETRY_API_URL=http://127.0.0.1:4100 and TELEMETRY_API_TOKEN to the Operator token, then run npm run demo:publish. This sends a finite 20-tick scenario across four devices, including an exceedance followed by recovery.

Use a separate browser session with the Reader token to observe the Operator's acknowledgement. Reader requests to write endpoints are refused by the server.

## API and storage contract

OpenAPI is generated by the running application at /api/v1/openapi.json. Authenticated routes:

| Method and route | Meaning |
| --- | --- |
| GET /api/v1/health | Database readiness, deployment type and authenticated role |
| GET, POST /api/v1/devices | Observe equipment or register an immutable threshold configuration |
| POST /api/v1/telemetry | Ingest a batch with event identifiers and provenance |
| GET /api/v1/telemetry | Device history with explicit time bounds |
| GET /api/v1/anomalies | Exceedance observations within a requested time window |
| GET /api/v1/alarms | Persistent alarm episodes, including acknowledgement and clearing timestamps |
| POST /api/v1/alarms/{id}/acknowledgements | Operator acknowledgement; actor comes from authentication |
| GET /api/v1/report | Operational counts and durations |

Epoch timestamps and durations use milliseconds. Temperatures use degrees Celsius; vibration uses mm/s. Only provenance=simulated is accepted. A real deployment is not a claim of real sensor acquisition.

An event identifier can be retried with the same payload without being counted twice. Reusing it for another payload returns a conflict. Device timestamps must advance; future timestamps beyond the validation tolerance are rejected. Batch writes, alarm transitions and audit events share a serializable SQL transaction.

An exceedance is strictly greater than its configured threshold. The first exceeding sample opens an episode, subsequent exceeding samples update its peak, and the first non-exceeding sample closes it. Acknowledgement and return to normal are separate facts. Repeated acknowledgement retains the first actor and timestamp.

Schema changes are additive and versioned in api/migrations. No migration drops historical data. Future migrations must remain compatible with the previous application version before rollback can be offered.

## Report rules and limits

The report's cohort consists of alarms raised between start and end, inclusive. By default this is the last 15 minutes.

- alarm_count counts episodes in that cohort, not samples.
- average_acknowledgement_ms is the arithmetic mean of acknowledged_at minus raised_at for acknowledged episodes only. Unacknowledged episodes are excluded.
- average_cleared_duration_ms is the arithmetic mean of cleared_at minus raised_at for cleared episodes only. Open episodes are excluded.
- An empty denominator returns null and the UI says there are no completed observations.

These are durations observed at sample boundaries, not an estimate of the exact physical crossing time. The UI divides milliseconds by 1,000 to display seconds. The anomalies endpoint calculates peak and sample count from observations inside the requested window, not the whole episode.

Queries span at most 24 hours. History refuses more than 10,000 returned observations; request a narrower window. Alarm and anomaly lists currently return at most 1,000 entries and have no pagination. This bounds the demonstration, but is not suitable for unbounded production retention.

## Verification

```sh
# Repository root: frontend and existing bridge
npm test
npm run lint
npm run build

# api/: HTTP boundary tests
npm test
npm run build

# api/: set SQL_CONNECTION_STRING to the dedicated test database first
npm run test:sql
```

For export/import integrity, set SQL_CONNECTION_STRING to the source database and SQL_RESTORE_CONNECTION_STRING to a different, empty database:

```sh
npx tsx --test test/recovery.test.ts
```

The recovery test validates the digest, compares the imported data and refuses a second import into a populated destination. It intentionally leaves the successful restore intact.

Read the recorded evidence and its limitations in this repository. Browser video and runtime results are demonstration evidence, not a claim of customer production experience.
